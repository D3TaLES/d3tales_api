Args:
fw_spec (dict): A Firework spec. This comes from the master spec.

In addition, this spec contains a special “_fw_env” key that contains the env settings of the FWorker calling this method. This provides for abstracting out certain commands or settings. For example, “foo” may be named “foo1” in resource 1 and “foo2” in resource 2. The FWorker env can specify { “foo”: “foo1”}, which maps an abstract variable “foo” to the relevant “foo1” or “foo2”. You can then write a task that uses fw_spec[“_fw_env”][“foo”] that will work across all these multiple resources.

d3tales_api.Workflows.Orca module

ORCA implementation of the D3TaLES electronic-structure FireTasks.

This module mirrors the workflow interface used by Gaussian.py and Psyscf.py, while executing calculations with the ORCA command-line program. It preserves D3TaLES/FireWorks naming, storage, geometry, hash, and update_spec conventions.

Runtime requirements:

  • ORCA installed and available as orca or configured with orca_cmd

  • Open MPI compatible with the installed ORCA release

  • NumPy, FireWorks, atomate, pymatgen, and the D3TaLES API package

ORCA output is parsed directly. GBW files are retained as native checkpoints; JSON records replace Gaussian formatted-checkpoint files.

d3tales_api.Workflows.pyscf module

PySCF counterpart of Gaussian.py (d3tales_api.Workflows).

Every FireTask in Gaussian.py has a PySCF twin here with the same task keywords, the same FWAction update_spec keys, and the same working-directory / file-name conventions:

Gaussian.py Psyscf.py ————————— ———————————————— GaussianBase PySCFBase RunGaussianEnergy RunPySCFEnergy RunGaussianOpt RunPySCFOpt (opt -> freq -> re-opt loop, max 5 runs) RunWtuning RunPySCFWtuning (uses PySCFWtuningJob, a WtuningJob subclass) RunGaussianTDDFT RunPySCFTDDFT (+ NTO analysis when run_nto is set)

What changes because the engine is PySCF (there is no Gaussian input/output text to write or parse):

  • <prefix>.com -> <prefix>.xyz (geometry input)

  • <prefix>.chk -> <prefix>.chk (PySCF HDF5 checkpoint)

  • <prefix>.fchk -> <prefix>.molden (what formchk produced; PySCF has no fchk writer)

  • <prefix>.log -> <prefix>.log (PySCF log + a Gaussian-style summary block at the end so the

    existing helpers in utils.py – parse_tddft, get_tddft_excitations, runtime_from_log – keep working on it)

  • Gaussian route keywords are translated: IOp(3/107,3/108) -> omega, SCRF=(PCM,Solvent=) -> IEF-PCM, SCF=(xqc,vshift,conver) -> SCF ladder, Opt -> geomeTRIC, TD(NStates,50-50) -> PySCF TDDFT.

  • Results are stored as local JSON records (see utils.save_local_result). PySCF output cannot be uploaded to the D3TaLES website (its parser reads Gaussian logs), so nothing is ever uploaded; the D3TaLES database is still used for READING (ground state, SMILES, geometry, omega).

Requires: pyscf, geometric (geomeTRIC; for geometry optimization), scipy (omega tuning).

Args:

In addition, this spec contains a special “_fw_env” key that contains the env settings of the FWorker calling this method. This provides for abstracting out certain commands or settings. For example, “foo” may be named “foo1” in resource 1 and “foo2” in resource 2. The FWorker env can specify { “foo”: “foo1”}, which maps an abstract variable “foo” to the relevant “foo1” or “foo2”. You can then write a task that uses fw_spec[“_fw_env”][“foo”] that will work across all these multiple resources.
