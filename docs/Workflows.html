Workflows

The Workflows module provides the Fireworks-based workflows for the high-throughput computational workflow that populated the D3TaLES database.

Modules

Important Fireworks-based modules include:

  • Calculation-specific modules for FireTasks:

    • Initialize: FireTasks for initialize molecules and getting basic molecular information

    • Gaussian: FireTasks for Density Functional Theory calculations with Gaussian

    • In development Gromacs: FireTasks for Molecular Dynamics simulations with Gromacs

  • D3TaLES_FW: defines all Fireworks

  • wf_writer: defines Workflows

The other modules are not of much importance for upper-level use because their functionalities are simply imported by the Fireworks based modules. But, to summarize, these modules include:

  • ParamSet: translates dictionary-based calculation parameters (e.g., functional, basis set, etc.) for use in workflow

  • wtuning: module adapted from the OCELOT API for performing IP fitting

  • utils: utility functions and environment variables

Setup

Config Directory

The directory where jobs are launched should also contain a config directory. This should contain fireworks configuration files, including FW_config.yaml, my_fireworker.yaml, and my_launchpad.yaml. The directory ex_config provides an example for the config directory. Remember, the config directory must be in the same parent directory as d3tales_fw.

Gaussian GPU jobs

Gaussian resource settings are optional FireWorker environment variables in my_fireworker.yaml, so each HPC worker can provide values that match its scheduler allocation. For example:

env:
  g16_cmd: /path/to/g16
  gaussian_gpu_cpu: "0-1=0,2"
  gaussian_cpu_list: "0-3"
  gaussian_memory: "48GB"
  gaussian_nprocshared: "4"

gaussian_gpu_cpu supplies Gaussian’s %GPUCPU value: the GPU indices, followed by =, then one distinct control CPU per GPU. gaussian_cpu_list supplies the complete allocated CPU list and must include those control CPUs. Both lists must match the resources assigned by that worker’s scheduler; the indices above are examples only. When GPU variables are omitted, tasks use CPU-only %NProcShared settings. gaussian_memory and gaussian_nprocshared are optional; absent values retain the task’s configured memory and default CPU count. The separate w-tuning task does not use these GPU settings.

Parameter file

The GausParamSet class generates object-based parameters for the Workflows module to use throughout the design and launch of calculation workflows. The object parameters, GausParamSet reads a JSON file containing job parameters. The first-level keys in this parameter file should be the job names and the values should be the associated parameters. For example, a JSON file with the following data would establish DFT parameters for opt_groundState and opt_cation1 jobs.

{
   "opt_groundState": {
        "route_parameters":{
            "opt": "",
            "scf(maxcyc=512)" : ""
        },
        "functional": "LC-wHPBE",
        "basis_set": "Def2SVP",
        "charge": 0,
        "multiplicity": 1
    },

  "opt_cation1": {
      "route_parameters":{
          "opt": "",
          "scf(maxcyc=512)" : ""
      },
      "functional": "LC-wHPBE",
      "basis_set": "Def2SVP",
      "charge": 1,
      "multiplicity": 2
  }
}

Charge and spin state: A task’s charge is a relative charge, added to the molecule’s ground-state charge. The configured multiplicity is authoritative; it is not replaced by an automatic singlet/doublet estimate. The workflow reports when its parity-derived estimate differs from the configured value and rejects a multiplicity that is incompatible with the electron-count parity. This permits valid higher-spin states such as triplets. Set charge and multiplicity in the task parameters, or override them with task kwargs or the FireWorks spec. restricted=False selects an unrestricted reference; it does not change the configured spin.

Geometry handoff: A task configured with geometry="X" consumes X_geom (or X_hash) from an upstream Firework. If that requested geometry is absent, the task fails rather than silently calculating from the SMILES geometry. The initial opt_mol optimization may use its supplied initial geometry and can generate a starting geometry from SMILES when none was supplied.

Adding a workflow

The following code submits a basic workflow.

import os
from fireworks.core.launchpad import LaunchPad
from d3tales_api.Workflows.wf_writer import d3tales_wf
from d3tales_api.Workflows.ParamSet import GausParamSet


BASE_DIR = "" # BASE_DIR must be defined 
lpad_file = os.path.join(BASE_DIR, 'config', 'my_launchpad.yaml')  # See notes about config directory 
param_file = os.path.join(BASE_DIR, 'parameter_file.json')

# Establish calculation parameters from parm_file json file
paramset = GausParamSet().from_json(param_file)

# Define Fireworks Workflow 
wf = d3tales_wf(paramset, smiles="CCCC", wtune=True, solvent='acetonitrile')

# Add the workflow to the Fireworks launchpad
info = LaunchPad().from_file(lpad_file).add_wf(wf)

Launch jobs

Once jobs are added to the launchpad, you can launch jobs from the commandline of any server with the Fireworks rlaunch commands. See the Fireworks documentation for more detail.
